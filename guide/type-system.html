Type system: Max for Live gaps

maxpylang’s type system checks cords as you type and when the script runs (see Checks and warnings). For Max for Live devices it still has gaps. The plugin generator (Plugin generator) records each one it meets, and each is pinned by a test, so the log below always matches the code. It is kept in docs/type-system/m4l-gaps.md, shown here as it is.

What maxpylang cannot yet say or check about a Max for Live device.

This log is fed by the plugin generator (web/interactive-plugin.html). The generator builds real audio effects with maxpylang, so every time it needs a workaround, or the checks pass a device that is broken, that is a gap, and it goes here.

How the loop works

  1. Find. A gap shows up as a workaround in web/src/plugin/fxgen.py (a comment reading gap M4L-NN), or as a broken device that save() accepts without a warning.

  2. Log. It gets an entry below: what is missing, the evidence, a proposed fix.

  3. Pin. It gets a test in tests/test_m4l_gaps.py that states the wanted behaviour and is marked xfail(strict=True).

  4. Close. When the gap is fixed its test starts passing, and strict xfail turns that into a failure. That failure is the reminder to remove the mark, set the status here to closed, and delete the workaround from fxgen.py.

tests/test_fxgen.py::test_named_gaps_are_the_ones_in_the_log keeps the two ends attached: every gap the generated script names must have an entry in this file.

The page shows the same thing to its users. Its “Type check” panel lists the gaps the current device had to work around, read off the generated script.

“Express” gaps block the generator and are worked around in its script. “Check” gaps do not block it: the generator happens to build correct devices, and the checks would not have noticed if it had not.

M4L-01: a dial’s range, unit and start value cannot be set

Missing. A live.dial is only useful with a range. Max keeps the range, the unit, the curve and the starting value in the Live parameter block, saved on the box under saved_attribute_attributes.valueof (parameter_mmin, parameter_mmax, parameter_unitstyle, parameter_exponent, parameter_initial, parameter_longname).

Evidence. dial.edit(saved_attribute_attributes={...}) prints Error: live.dial : saved_attribute_attributes is not a valid attribute argument and drops it. The rejection is a print, not a warning or an exception, so a script cannot detect it and the device saves with every dial at Max’s default of 0 to 127.

Workaround. obj._dict["box"]["saved_attribute_attributes"] = {...}.

Proposed fix. A typed parameter on the object, for example dial.parameter(name, lo, hi, initial, unit, exponent), shared by every live.* object. Separately, make edit() warn (UnknownAttributeWarning) instead of printing. Once ranges are first-class, M4L-07 and M4L-08 become checkable.

Tests. test_m4l_01_a_dial_range_can_be_set, test_m4l_01_a_rejected_attribute_is_not_silent.

M4L-02: presentation mode has no API and is rejected on some objects

Missing. A device’s interface is its presentation view: each visible box needs presentation: 1 and a presentation_rect. Background panels also need background: 1.

Evidence. edit(presentation=1, presentation_rect=[...]) works on live.dial and live.comment, and is rejected on panel (Error: panel : presentation is not a valid attribute argument). The difference is whether the object’s scraped attribute list contains the COMMON marker, which is an accident of the scrape. Presentation is a property of every box.

Workaround. Write the three keys straight into the box dict.

Proposed fix. obj.present(x, y, w, h) on MaxObject, valid for every box, with the rect checked as four numbers. Accept the common box attributes on every object whether or not its data file lists COMMON.

Test. test_m4l_02_any_box_can_be_put_in_presentation.

M4L-03: a comment is saved with its object name in front of its words

Missing. patch.place("comment Filter") should make a comment that reads “Filter”.

Evidence. The saved box has "text": "comment Filter". Max stores only the words there: the comments in this repo’s own Max-saved examples read "text": "dry", "text": "delay". The same happens to live.comment, and to every UI object, which is saved with a text key holding its own name ("text": "live.dial"). For most UI objects Max ignores the stray key. For the two comment objects text is the content, so the name is displayed. edit() also rewrites the key, so setting it by hand has to come after any edit() call, which is how the generator found this.

CLAUDE.md recommends patch.place("comment === SECTION NAME ===") for section headers, so this affects ordinary patches, not only devices.

Workaround. obj._dict["box"]["text"] = "Filter", after the last edit().

Proposed fix. For comment and live.comment, save the arguments as text. For other UI objects, do not write text at all.

Test. test_m4l_03_a_comment_saves_only_its_words (both objects).

M4L-04: patcher settings have no API

Missing. Two patcher-level keys decide how Live shows a device: openinpresentation (without it Live shows the patching view, squeezed into the device strip) and devicewidth.

Evidence. MaxPatch has no public method that reaches them. save() writes whatever the template had (openinpresentation: 0).

Workaround. patch._patcher_dict["patcher"]["openinpresentation"] = 1.

Proposed fix. Either a general patch.set_attribs(openinpresentation=1, ...), or have save(device_type=...) turn openinpresentation on when any box is in presentation, and compute devicewidth from the presentation rects. The test pins the second option; the first would also close it once the test is adapted.

Test. test_m4l_04_a_device_with_a_presentation_opens_in_it.

M4L-05: a tap link is not a type

Missing. tapin~’s outlet does not carry audio or numbers. It carries a tap link (Max’s tapconnect), and the only thing that understands one is tapout~. Every delay, chorus and flanger in a device is built on this pair.

Evidence. tapin~ -> *~ is accepted by the cord check as a checked, unflagged cord. A tapout~ fed by no tapin~ is accepted too, although it has no line to read and outputs silence. The data already knows the outlet’s type: the xlet’s _types is 'tapconnect'.

Proposed fix. Give tapconnect its own cord type in the cord check: an outlet of that type may only reach an inlet that accepts it. Add a graph rule that a tapout~ must be reachable from a tapin~ through a tap link.

Tests. test_m4l_05_a_tap_link_only_fits_a_tapout, test_m4l_05_a_tapout_needs_a_tapin.

M4L-06: the device type is not a contract

Missing. device_type says what the device is for, which fixes what it must contain:

device_type

must read

must write

audio_effect

plugin~

plugout~

instrument

a MIDI input (notein, midiin)

plugout~

midi_effect

a MIDI input

a MIDI output

Evidence. An “instrument” that is cycle~ 440 -> plugout~, with no MIDI input at all, saves with no warning. So does an “audio effect” that never reads plugin~.

Part of this is already done, and it is worth saying so: the graph check knows that inside a device dac~ and ezdac~ are not outputs, and reports audio that only reaches them as reaching nothing (test_ezdac_in_a_device_is_caught). The message does not yet say “use plugout~”.

Proposed fix. Treat device_type as a signature and check it in save(): required sources and sinks per type, each with a message that names the object to add.

Tests. test_m4l_06_an_instrument_needs_midi_in, test_m4l_06_an_audio_effect_needs_audio_in.

M4L-07: a parameter’s range is invisible to the checks

Missing. The checks type a cord by rate (audio or not). They know nothing about the values on it. In a device nearly every control cord starts at a dial with a declared range and ends at an inlet with an expected one.

Evidence. A dial declared as 40 to 18000 (Hz) wired into svf~’s resonance inlet, which takes 0 to 1, saves with no warning. The generator avoids this only because one table (schema.json) is the single source of each dial’s range.

It then happened for real. The first version of the generator shipped four dials whose range ran past what the object behind them accepts, and nothing said so:

Dial

Declared

What the object takes

Filter Cutoff into svf~

up to 18000 Hz

up to a quarter of the sample rate (11025 Hz)

Distortion Tone into onepole~

up to 18000 Hz

the same

Reverb Damp into onepole~

up to 16000 Hz

the same

Distortion Drive into overdrive~

up to 12

1 to 10

In Live the top third of each of those dials would have turned and changed nothing. They were found by reading Max’s reference pages, which state each limit in prose. The limits are in the scraped reference data already, as text; this gap is about turning them into something a check can read. A fifth case was a matter of degree, not of limits: svf~’s resonance is nominally 0 to 1, and measured in Max it is flat below 0.17 and rings for seconds above 0.85, so the dial now maps onto 0.17 to 0.75.

Proposed fix. This is the refinement the formal model leaves open. A first step that does not need full interval typing: record the documented range of the few dozen inlets where it matters (resonance, feedback, gain coefficients), read the dial’s range from its parameter block, follow it through the arithmetic objects that have an obvious interval rule (* k, + k, scale, !- k), and warn when the intervals do not overlap. Depends on M4L-01.

Test. test_m4l_07_a_dial_range_is_checked_against_its_inlet.

M4L-08: duplicate parameter names are accepted

Missing. Live identifies a parameter by its long name. Two parameters with the same long name collide: automation and mappings attach to the wrong one, and Max renames one of them on load.

Evidence. Two dials both named “Gain” save with no warning.

Proposed fix. A patch-level check in save() for devices: long names unique across all objects with parameter_enable. Depends on M4L-01.

Test. test_m4l_08_parameter_names_are_unique.

M4L-09: output level is unbounded

Missing. CLAUDE.md states a rule for every device: clip~ -1. 1. before plugout~, for speaker safety. It is a convention; nothing enforces it.

Evidence. plugin~ -> *~ 4. -> plugout~ saves with no warning.

Proposed fix. A lint in the graph check for devices: every path into plugout~ passes through an object that bounds amplitude (clip~, limi~, tanh~, overdrive~). Reported as advice, not as an error, because a device that only attenuates is safe without one.

Test. test_m4l_09_output_level_is_bounded.

M4L-10: a parameter that controls nothing is accepted

Missing. A live.dial with no cord leaving it is a knob in Live that does nothing.

Evidence. The graph check reports other objects whose output reaches nothing, and does not report a disconnected dial, because a UI object counts as a display.

Proposed fix. For objects with parameter_enable, being visible is not enough: require a cord from an outlet, or a varname that something refers to.

Test. test_m4l_10_a_parameter_controls_something.

M4L-11: audio objects whose inlets have no type

Missing. A type for the inlet of about fifty audio objects, among them tanh~, cosh~, sinh~, tanx~, sinx~, cosx~, receive~ and gen~.

Evidence. cycle~ -> tanh~ was reported as a cord the checks could not judge (“no type data”), on an object that takes a signal and nothing else. The cause is upstream: the reference pages Max ships for these objects have a placeholder where the inlet type goes (<inlet id="0" type="INLET_TYPE">), so the type table records the inlet as any. 53 objects in msp-ref have both the placeholder and an any inlet.

It showed up as soon as the generator used tanh~ for its tube distortion and for the saturating delay loop: the page’s “Type check” panel went from “all cords checked” to “2 not checked”.

Done so far. tanh~’s inlet is set to signal in data/xlet_types.json, by hand, after confirming in Max that it processes audio.

Proposed fix. The same pages describe each inlet in their method list (<method name="signal">), and for most of the fifty that is enough to tell a signal inlet from a message inlet. Use it as a fallback when the inlet type is the placeholder.

Tests. test_m4l_11_tanh_is_judged (passes), test_m4l_11_a_cord_into_cosh_is_judged.

A gap the checks caught

Worth recording because it is the loop working in the other direction. While the filter was being reworked, a control object in the generated script was given the same variable name as the Reso dial. Every cord written against the dial landed on the new object instead, so the dial fed nothing and the object fed itself. The graph check reported it on the next build (“hot loop through scale: every cord lands on a hot inlet”), and seven presets failed their test. The generator now refuses a name used twice.

Outside the type system

Found on the same pass. These are about the browser engine in web/, not about maxpylang’s types, and are listed so they are not lost.

  • The web object manifest is behind the library. web/scripts/gen-manifest.mjs no longer runs against the current OBJ_INFO: it refuses the p alias, which the library now has, and it does not walk the m4l package at all. Regenerating with both fixed changes the arity rule count from 46 to 87 and breaks 21 web tests, so it is its own piece of work. Until then the live.* objects the page needs are registered by hand (objects/ui/live-dial.ts, objects/audio/plug.ts).

  • A signal into an inlet adds to the argument instead of replacing it. In Max a signal connected to *~ 0.5’s right inlet replaces the 0.5. In the engine the signal is connected to an AudioParam, which sums with the value it already holds. The generator avoids the difference by giving an object no argument (or 0) wherever a signal drives that inlet.

  • A feedback loop runs 128 samples late in the browser. Chrome adds one render quantum to every cycle in the audio graph, so each repeat of a tapin~ / tapout~ echo arrived 2.9 ms after it does in Max, and a reverb built on looped delays came out detuned. tapout~ now has an early read for the cords that close a loop, and comb~ is a worklet with its loop inside.

  • The preview is checked against Max, not assumed. web/scripts/maxcheck/ renders one test signal through the same generated patches in Max and in the engine and compares the recordings. The filter, every distortion type, the crusher, the delay, the flanger and the reverb now match a Max 9 recording to its last bit. What still differs (where an LFO starts, and a one-vector offset inside Max) is listed in that folder’s README, along with the formulas the measurements gave for svf~, overdrive~, onepole~, degrade~, comb~ and allpass~.
